# M1 optimisation ledger

This is a record of the measured M1 work, not a claim about the current tree.
`proj/m1/` is immutable historical source. M2 is built only from the separate
`proj/m2/` tree; no M1 number can be relabelled as an M2 result.
The source record is [`results/bench/run-581897`](../results/bench/run-581897/).

## Run conditions

- Captured 2026-09-03 08:15 UTC on Rangpur node `a100-0`, one task and one CPU
- GCC 13.3.1, CMake 3.26.5, fixed `-O3 -DNDEBUG -march=native -flto=1` evidence build
- One sample per row and a 100 ms minimum case time
- The benchmark harness passed `--seed 31` to every child, overriding the scenario's configured seed
- The captured tree was dirty at `c3d04c1db04fea5d3e72923a696d2944d6f04b6f`; do not describe these numbers as a clean-tree baseline

The harness checked the scenario checksum within and between samples. The L0–L7 predator-prey rows all produced `cf299cf42034d25c`.

Evidence: [`provenance.csv`](../results/bench/run-581897/provenance.csv), [`levels.csv`](../results/bench/run-581897/levels.csv), [`docs/performance.md`](performance.md).

Some generated M1 figures label the workload as seed 7. That label is inaccurate for this recorded run: `benches/bench.cpp` defaults to seed 31 and passes it to `m1`; `cmdline.cpp` applies an explicit `--seed` after loading the scenario. Use seed 31 when reproducing or presenting this run.

## Cumulative ladder

The workload is `continuous/predator-prey/100k`: 100,000 active entities for 10 steps, or 1,000,000 entity updates. A level enables its mechanism and all earlier mechanisms. The figures show the data-layout changes; they are not profiling evidence.

| Level | Change | Throughput (M updates/s) | Speedup vs L0 |
| --- | --- | ---: | ---: |
| L0 | Linked cell lists with 64-bit indices | 2.792 | 1.000× |
| L1 | Contiguous cell membership | 3.023 | 1.083× |
| L2 | Sparse grid reset | 2.953 | 1.058× |
| L3 | Type-split contiguous ranges and 32-bit indices | 3.807 | 1.363× |
| L4 | Fast fixed 3×3 stencil | 3.174 | 1.137× |
| L5 | Reciprocal two-population pair kernel | 4.830 | 1.730× |
| L6 | Verlet candidate cache | 8.710 | 3.120× |
| L7 | CSR candidates and movement certificates | 10.315 | 3.695× |

L2 and L4 were slower than the preceding levels in this one run. They remain in the cumulative sequence; this result alone does not isolate their cost because each row is measured only against its preceding source level. The largest observed step is L5→L6. L6 rebuilt one pair list and evaluated 1,539,411 pairs; L7 rebuilt one list, evaluated 1,640,031 pairs, and used 5,835,852 bytes for its pair list. Those counters belong only to this workload.

Evidence: [`levels.csv`](../results/bench/run-581897/levels.csv), [`optimisation-map.svg`](../results/bench/run-581897/optimisation-map.svg), [`l0-linked.svg`](../results/bench/run-581897/l0-linked.svg) through [`l7-csr.svg`](../results/bench/run-581897/l7-csr.svg).

## Scaling and pages

Conway's 10-step throughput rose from 4.623 M cell-updates/s at 1K cells to 5.083 at 1M, stayed near 5.044 at 10M, then measured 4.226 at 100M and 4.249 at 1B. Peak RSS rose from 4.6 MiB to 36,243.9 MiB. The measurement shows a throughput change as the state becomes large; it does not identify a cache boundary or cause.

At 10M cells, the verified base-page run measured 5.095 M cell-updates/s and the verified huge-page run 5.047 M: huge/base = 0.991×. Both runs had matching checksum `953643c1b0c48b59`; Linux reported 4 KiB host pages and the requested backing was verified. Huge pages were not an improvement in this single sample.

Evidence: [`scaling.csv`](../results/bench/run-581897/scaling.csv), [`pages.csv`](../results/bench/run-581897/pages.csv), [`scaling.svg`](../results/bench/run-581897/scaling.svg), [`pages.svg`](../results/bench/run-581897/pages.svg).

## Limits carried forward

- One sample means the reported confidence intervals and coefficient of variation are mechanically zero; they are not estimates of run-to-run variation
- The ladder compares cumulative variants on one predator-prey input, not each mechanism across scenes or densities
- Conway scaling does not measure the continuous kernel, and the ladder does not measure Conway, Heston, chess, or carrom
- Peak RSS is process-level maximum resident memory from `wait4`; it cannot explain allocation lifetime or cache behaviour
- No profiler output or hardware-counter capture accompanies this run, so hotspot and microarchitectural claims remain unproven
- The page result is valid only for this node, workload, policy, and one sample

## Reproduction rule

Run the recorded collector inside Slurm with at least five samples and a 1,000 ms minimum case time before quoting a replacement result:

```bash
SAMPLES=5 MINIMUM_CASE_MS=1000 tools/scripts/test.sh bench
```

Keep the resulting `levels.csv`, `scaling.csv`, `pages.csv`, `provenance.csv`, job logs, and checksum gates together. [`docs/performance.md`](performance.md) defines the report schema and rejection conditions.
