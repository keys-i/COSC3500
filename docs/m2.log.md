# M2 optimisation ledger

## 2026-09-24 — M2 scope

M2 parallelises the L7 continuous-kernel CSR reuse loop with OpenMP on one UQ cluster node. It is an independent program: `proj/m2/` compiles to `m2` and must never use `proj/m1/` objects or source as its measured implementation. This is a narrow claim about `continuous/predator-prey/100k`, not a claim that every kernel or scene scales the same way.

The serial grid build and CSR construction remain serial. During CSR reuse, OpenMP statically partitions entity indices. Each worker reads current state and immutable CSR ranges, writes only its own next-state entries, and retains local counters and displacement maxima; deterministic serial work completes before the checksum. The build switch is `HPC_M2_OPENMP=ON`.

Historical Rangpur measurements collected before the source split used a temporary M1-named implementation. They were planning evidence only. The independent M2 measurements below use the `m2` binary and must not be combined with those historical rows.

CUDA and MPI are deferred as alternative parallel techniques, not as a replacement for OpenMP. They need separate measured evidence: device-transfer and kernel timing for CUDA; domain decomposition, communication, load balance, and cross-rank correctness for MPI.

## Hypothesis and controls

Hypothesis: for the fixed L7 CSR-reuse workload, static OpenMP ownership reduces elapsed time as worker count rises, while preserving the serial checksum for each seed.

Controls:

- Workload: `continuous/predator-prey/100k`, 100,000 entities and 10 steps
- Builds for the next profile run: M2 L0 serial, M2 L7 serial, and M2 L7 OpenMP; all use the same fixed release flags
- Seeds: 31, 32, and 33
- Threads: 1, 2, 4, and 8, pinned with `taskset`; `OMP_PROC_BIND=close` and `OMP_PLACES=cores`
- Sampling: five samples, one warm-up, and a 1,000 ms minimum case time by default
- Correctness: each M2 L7 serial/OpenMP checksum must equal M2 L0 for the same seed
- Provenance: retain node, CPU description, affinity, compiler version, command lines, flags, and perf availability

The harness explicitly passes the selected seed to each benchmark child. Seed 31 is the historical M1 run seed; it is not inferred from the scenario file.

## Measurement path

Run the purpose-built M2 script from an allocated Linux UQ cluster node:

```bash
tools/scripts/profile
```

It writes one timestamped directory below `results/profile/` containing `provenance.txt`, commands, raw benchmark CSVs, `timing.csv`, `strong-scaling.csv`, checksum checks, and attempted `perf` counters and call stacks. If `perf` is unavailable or denied, timing data is retained and the script reports that limitation rather than inventing a profile.

The current script compares M2 L0 with M2 L7 serial at one thread, then runs
M2 L7 OpenMP at every seed/thread tuple. It rejects checksum differences
before writing the scaling summary. L0 to L7 measures serial optimisation
within M2; OpenMP p1 to p8 measures parallel scaling within M2. The older
M1 L0 to M2 L7 run below remains cross-codebase context. Raw paths, rather
than copied values, are the source for the M2 slides and report.

## Scaling analysis plan

For each seed and thread count, calculate strong-scaling speed-up `S(p) = T(1) / T(p)` and efficiency `E(p) = S(p) / p` from the L7 OpenMP median times. Plot all three seeds or state why a seed is unavailable; do not hide a changed ranking behind an average.

Use Amdahl's law, `S(p) <= 1 / (f + (1 - f) / p)`, to explain the serial grid/CSR work, synchronisation, and imbalance that cap fixed-size speed-up. Use Gustafson's law, `S_G(p) = p - f(p - 1)`, only after an additional fixed-work-per-thread experiment has been run. It is a planning model, not evidence of weak scaling.

Profile the same workload and tuple used for the timing claim. If hardware counters are inaccessible, use a separately compiled, explicitly labelled phase-timing diagnostic and do not treat its instrumented times as release timings.

## 2026-09-24 — independent M2 strong-scaling run with historical M1 baseline

Hypothesis: static OpenMP ownership of the CSR reuse path reduces elapsed time without changing results. The tested case is ten steps of 100,000 predator/prey entities at fixed density. The controls above were met on UQ Rangpur node `vcpu-5`: eight allocated logical CPUs `0-7` of an AMD EPYC 7542 virtual machine, one NUMA node, Linux `4.18.0-553.150.1.el8_10.x86_64`, GCC 13.3.1. `HPC_FIXED_RELEASE_FLAGS=ON` and release flags were used for all three builds; `M2_OPT_LEVEL=7`, `HPC_M2_OPENMP=OFF/ON`, `OMP_DYNAMIC=false`, static scheduling, and pinned CPU sets make the comparison reproducible. The precise build invocations, affinity, compiler, and environment are in `results/profile/run-20260924T110021Z-rG8ANs/`.

Each tuple has five timed samples following one warm-up and a one-second minimum case. Each seed's M1 L0, M2 L7 serial, and M2 L7 OpenMP 1/2/4/8 runs produced exactly the same checksum: seed 31 `cf299cf42034d25c`, seed 32 `71694acd167d9539`, seed 33 `31321f12775b1892`. Different seeds therefore exercise different initial states without changing the cross-variant result. The aggregate below is the median of the three seed medians; speed-up is the median of matched, same-seed ratios, not a ratio of unrelated populations.

| Variant | Threads | ns/entity-update | Matched speed-up vs M2 OpenMP p1 | Efficiency |
| --- | ---: | ---: | ---: | ---: |
| M1 L0, historical baseline | 1 | 358.239 | — | — |
| M2 L7, serial | 1 | 94.945 | — | — |
| M2 L7, OpenMP | 1 | 95.185 | 1.000× | 100.0% |
| M2 L7, OpenMP | 2 | 67.600 | 1.410× | 70.5% |
| M2 L7, OpenMP | 4 | 53.846 | 1.773× | 44.3% |
| M2 L7, OpenMP | 8 | 52.131 | 1.826× | 22.8% |

M2 OpenMP p1→p8 is a **within-M2 parallel** gain of 1.826×. M1 L0→M2 OpenMP p8 is a 6.863× **cross-codebase, combined serial-plus-parallel** comparison, not an OpenMP gain. The M2 serial build was slightly faster than its OpenMP p1 build (94.945 vs 95.185 ns/entity-update), consistent with a small OpenMP-path cost; this run cannot isolate instruction-level or compiler effects. For the 8-thread point, the three seed medians were 51.735, 52.131, and 52.597 ns/entity-update. At four threads, seed 33 had a noisier five-sample coefficient of variation of 3.98%; retain that row rather than hiding it in an aggregate. All per-seed medians, bootstrap confidence bounds, variability, state and pair-list metrics are in `profile-summary.csv`.

The benchmark originally wrote an invalid `timing.csv` because its Bash formatter embedded an unquoted comma-separated CPU list. The raw per-tuple CSVs were intact. `profiles.py` now validates those raw rows and regenerates valid `timing.csv` and `strong-scaling.csv` with a CSV writer. This is a reporting repair, not a rerun or a changed measured value.

`continuous-baseline.cpp` in this run directory is the exact **M2** continuous kernel source before the bounded CSR-scratch candidate. It is an evidence snapshot, not an M1 source file and not part of the built candidate.

`perf stat` was installed but its first requested counters were `<not counted>`; `perf-status.txt` records that. There is no usable cycle/cache/branch count or sampled call stack from this run. The CPU advertises AVX2, but that does not establish vectorisation of this branch-heavy search. No cache-miss, memory-bandwidth, or vectorisation claim follows from the elapsed times alone.

Decision: accept OpenMP p2/p4/p8 as a correct, measurable M2 parallel implementation, but reject any claim of near-linear scaling. The p4→p8 improvement is small relative to the extra workers, so the next question is which serial phase caps this fixed-workload result.

## 2026-09-24 — phase diagnostic and next hypothesis

The diagnostic was built separately with `HPC_M2_PHASE_PROFILE=ON`; it is **not** the release binary whose ns/entity-update figures appear above. `results/profile/phase-615532/` contains five single-run traces per seed/variant/thread tuple. Its reporter cross-checks the checksum against the release run and validates each measured subtotal against its containing phase. The numbers here are medians of measured per-run shares, not ratios of independently aggregated medians.

At p1, CSR rebuild took about 33.6 ms of an 89.1 ms instrumented step, or 37.7%; CSR reuse/publish took about 55.5 ms, or 62.2%. At p8, rebuild remained about 33.5 ms while reuse/publish fell to 10.6 ms; rebuild therefore occupied about 75.8% of the 44.2 ms instrumented step. One rebuild occurs in the ten-step case. Within that rebuild on p8, first grid/count traversal took about 14.0 ms (42% of rebuild), the second grid/fill traversal about 10.8 ms (32%), and other rebuild work about 8.7 ms (26%). This is a wall-time phase attribution, not a hardware-counter hotspot. Instrumentation perturbs timings, so these milliseconds must never be divided into release elapsed time or compared directly with a release microbenchmark.

Hypothesis: retain accepted CSR edges from the first traversal in a bounded scratch buffer and fill the adjacency from those edges, avoiding the second grid traversal when scratch fits; otherwise keep the original second traversal. The next experiment must compare the original release M2 binary and the candidate binary on the same node, with interleaved seeded tuples and exact checksum equality. Accept only a useful p8 improvement without a material p1 regression or memory-budget breach; a shorter code path is not evidence of faster execution.

## 2026-09-24 — fixed-density size and weak scaling

`results/profile/size-scaling-20260924T121852Z-foIDpY/` is an independent M2 L7 release run on the same `vcpu-5` node (Slurm job 615598, exit 0, 11 minutes). It varies population from 100K to 800K, scaling the square world's area with population to hold expected density constant. Sensing radius (80), ten steps, seeds 31/32/33, build flags, pinning, one warm-up and five timed samples per tuple remain unchanged. The reporter checked exact serial/OpenMP p1/p2/p4/p8 checksum equality for every seed and size before producing the tables. The reported figures are medians across seed medians or median same-seed speed-ups, not pooled run samples.

| Entities | M2 OpenMP p1 ns/entity-update | M2 OpenMP p8 ns/entity-update | p1→p8 speed-up | p8 efficiency |
| ---: | ---: | ---: | ---: | ---: |
| 100K | 94.684 | 51.700 | 1.831× | 22.9% |
| 200K | 101.307 | 53.689 | 1.885× | 23.6% |
| 400K | 110.450 | 59.458 | 1.855× | 23.2% |
| 800K | 120.254 | 65.394 | 1.836× | 22.9% |

At fixed density, p1 cost per entity rises 27.0% from 100K to 800K; p8 cost per entity rises 26.5%. Thus the roughly 1.8× p1→p8 ratio persists, but absolute per-entity performance degrades with population. The raw timings establish this effect, not its microarchitectural cause: `perf` counters were unavailable, so cache or memory-bandwidth explanations remain hypotheses. Size-dependent rebuild and working-set costs are candidates for further measurement, not established facts.

For a weak-scaling comparison, grow the problem and worker count together: 100K/p1, 200K/p2, 400K/p4, 800K/p8. With constant density and ten steps, elapsed time should stay near the 100K/p1 reference under ideal weak scaling. It instead rises to 1.535×, 2.772×, and 5.520×, giving 65.2%, 36.1%, and 18.1% weak-scaling efficiency. This poor result is compatible with the unchanged serial rebuild, but the experiment does not by itself prove that rebuild is the only cause. Report both the nearly flat strong-scaling ratio and the poor weak-scaling result; presenting only the former would hide the important size effect.

The run used the pre-scratch-candidate M2 source. Any accepted candidate needs a separate size-scaling rerun before claiming improved scaling over these four sizes.
